Research date: 2026-11-08. Method notes: GitHub repo pages were read directly via web fetch (star counts are as displayed on the page on 2026-11-08). arxiv.org, huggingface.co and api.github.com could NOT be fetched from this session (blocked by network policy), so paper details come from search-result snippets of arXiv/CVF/IJCAI/ECCV pages and from GitHub READMEs. ## Q1. Per-model facts: repo, license, stars, weights, training scripts, reference count, resolution, style-deviation handling, compute

### Takeaway
Almost every dedicated few-shot font generator (DG-Font, LF/MX-Font, FsFont, CF-Font, VQ-Font, IF-Font, MSD-Font, FontDiffuser) is trained on Chinese (some Korean) glyph sets rendered from TTF fonts, and most ship training code but no pretrained weights; only FontDiffuser clearly releases weights, and it is non-commercial-only. None of them was trained on Arabic, so for this project they are "architectures to retrain", not ready-to-use tools.

### Cited Findings

**Classic GAN / non-diffusion few-shot models**
- **clovaai/fewshot-font-generation (FFG-benchmarks)**: unified repo containing FUNIT (ICCV'19), DM-Font (ECCV'20), LF-Font (AAAI'21), MX-Font (ICCV'21); 275 stars, 50 forks; **MIT license** (Copyright NAVER; FUNIT parts adapted from NVlabs/FUNIT); pretrained weights not mentioned on the README; languages named are Korean and Chinese; DM-Font is "suited to complete compositional scripts such as Korean" and needs code changes for Chinese; defines few-shot as "less than 10 glyph images" — [GitHub clovaai/fewshot-font-generation](https://github.com/clovaai/fewshot-font-generation)
- LF-Font official repo also exists separately — [GitHub clovaai/lffont](https://github.com/clovaai/lffont). LF-Font TPAMI extension reports good results with component-wise style factors from only eight reference glyphs — [TPAMI: Few-Shot Font Generation With Weakly Supervised Localized Representations](https://dl.acm.org/doi/10.1109/TPAMI.2022.3196675)
- **DG-Font (CVPR 2021)**: [GitHub ecnuycxie/DG-Font](https://github.com/ecnuycxie/DG-Font); 251 stars, 51 forks; no license stated on page; weights not mentioned; users render their own data from TTFs with `font2img.py` (README points to Founder Type Chinese fonts, "free for non-commercial users"); **"the current repo only works with 80x80 resolution images"** (DGFont++ with 128/256 "coming soon"); requires a deformable-convolution (DCN) library. DG-Font includes a "feature deformation skip connection" motivated by cursive characters — [search snippet summarizing DG-Font](https://www.researchgate.net/publication/352832088_Few-Shot_Font_Generation_with_Deep_Metric_Learning)
- **FsFont (CVPR 2022, "Few-Shot Font Generation by Learning Fine-Grained Local Styles")**: [GitHub tlc121/FsFont](https://github.com/tlc121/FsFont); 84 stars; license file present but not named on page; no weights link; built on **PaddlePaddle 2.3.2** (plus torch for plotting); user must build content-reference mappings, every content char needs the same number of references (example uses 3). Method treats each spatial location of the reference feature map as a fine-grained local style representation — [CVPR 2022 paper](https://openaccess.thecvf.com/content/CVPR2022/papers/Tang_Few-Shot_Font_Generation_by_Learning_Fine-Grained_Local_Styles_CVPR_2022_paper.pdf)
- **CF-Font (CVPR 2023)**: [GitHub wangchi95/CF-Font](https://github.com/wangchi95/CF-Font); 145 stars; no license stated; **no pretrained weights** (you train a base network, then CF-Font); data = GB/T 2312 set of **6,763 Chinese characters**, 240 seen fonts for training / 60 unseen for test (Founder Type fonts); uses **16 reference characters** per font (FS16); trains with DDP (multi-GPU implied, no VRAM figure).
- **VQ-Font (ICCV 2023)**: [GitHub Yaomingshuai/VQ-Font](https://github.com/Yaomingshuai/VQ-Font); 63 stars; no license stated; **no weights** (you pre-train the VQGAN yourself); Founder Type Chinese TTFs; reference set of **~100 characters**, 3 selected per target character.
- **IF-Font (NeurIPS 2024)**: [GitHub Stareven233/IF-Font](https://github.com/Stareven233/IF-Font); 42 stars; **MIT**; weights not stated; uses CompVis VQGAN (f=8, Z=256); "only uses 3500 common [Chinese] characters", split into two subsets; CUDA 11.8.
- **One-shot / cross-lingual predecessors**: AGIS-Net (one-shot artistic glyph synthesis) and FTransGAN ("Few-shot font style transfer between different languages") are known GitHub projects ([hologerry/AGIS-Net](https://github.com/hologerry/AGIS-Net), [ligoudaner377/font_translator_gan](https://github.com/ligoudaner377/font_translator_gan)) — repo pages were not fetched this session; see Gaps.
- **One-Shot Multilingual Font Generation via ViT** (Wang & Liu, arXiv 2412.11342, 15 Dec 2024): two ViT encoders (content + style), MAE pretraining, Retrieval-Augmented Guidance; covers Chinese, Japanese, English (Korean coverage inconsistent in the text — "in the pretraining phase, we skipped Korean"); 308 styles; also "user-invented glyphs". No Arabic — [arXiv 2412.11342](https://arxiv.org/pdf/2412.11342); [search summary](https://www.themoonlight.io/es/review/one-shot-multilingual-font-generation-via-vit)

**Diffusion-based font generators**
- **Diff-Font** (He et al., arXiv 2212.05895, Dec 2022): described as the first diffusion model for one-shot font generation; frames it as conditional generation; improves on intricate characters but has low inference efficiency — [arXiv 2212.05895](https://arxiv.org/pdf/2212.05895); [Semantic Scholar](https://www.semanticscholar.org/paper/Diff-Font:-Diffusion-Model-for-Robust-One-Shot-Font-He-Chen/e8a266462d218fe99cad961f913f9d3f9e6486db). A search result claimed official code on GitHub; a candidate repo is [Hxyz-123/Font-diff](https://github.com/Hxyz-123/Font-diff) but its link to Diff-Font was not verified.
- **FontDiffuser (AAAI 2024)**: [GitHub yeungchenwa/FontDiffuser](https://github.com/yeungchenwa/FontDiffuser); **579 stars**, 59 forks (most popular repo in this category); **no OSS license — "can only be used for non-commercial research purposes"**, commercial use requires contacting Prof. Lianwen Jin; **pretrained weights released** (unet.pth, content_encoder.pth, style_encoder.pth + SCR module) on Google Drive/BaiduYun; phase 1 & 2 training scripts released (SCR pretraining "coming soon"); trained on Chinese characters; demonstrates cross-lingual Chinese→Korean; **one-shot** (one style reference image); PyTorch 1.13.1 / CUDA 11.7; last dated README entry 2024-01-27. Method: Multi-Scale Content Aggregation + Style Contrastive Refinement — [arXiv 2312.12142](https://arxiv.org/pdf/2312.12142)
- **MSD-Font (CVPR 2024, "Generate Like Experts: Multi-Stage Font Generation by Incorporating Font Transfer Process into Diffusion Models")**: [GitHub fubinfb/MSD-Font](https://github.com/fubinfb/MSD-Font); 50 stars; **MIT**; **no trained weights released** (needs SD 2.1 autoencoder `v2-1_512-ema-pruned.ckpt`); Chinese example data, Founder Type fonts, FFG-benchmarks layout; stage 2 uses model parallelism across **two GPUs**; stage 1 ≥80 epochs, stage 2 5–20 epochs — [CVPR 2024 paper](https://openaccess.thecvf.com/content/CVPR2024/papers/Fu_Generate_Like_Experts_Multi-Stage_Font_Generation_by_Incorporating_Font_Transfer_CVPR_2024_paper.pdf)
- **DP-Font (IJCAI 2024)**: Chinese calligraphy generation with a diffusion model + physics-informed neural network; stroke-order constraints and physical constraints in the loss; slightly above Diff-Font in its tables — [IJCAI 2024 paper](https://www.ijcai.org/proceedings/2024/0863.pdf). No code repo found in this session.
- **HFH-Font** (arXiv 2410.06488, SIGGRAPH Asia 2024): few-shot Chinese font synthesis, latent-space (not pixel-space) diffusion, component-level style transfer, explicitly targets higher resolution and faster speed — [arXiv 2410.06488](https://arxiv.org/pdf/2410.06488)
- **DiffCJK** (arXiv 2404.05212): conditional diffusion generating CJK glyphs in a target style from a single reference glyph — [arXiv 2404.05212](https://arxiv.org/pdf/2404.05212)
- **FontStudio (ECCV 2024, Microsoft)**: shape-adaptive diffusion for *font effects* (texture/decoration inside irregular glyph shapes) using a segmentation mask as condition, plus a training-free "shape-adaptive effect transfer" that moves texture from one generated reference letter to the other letters for consistency; user study vs Adobe Firefly: 78% vs 10% win in aesthetics, 66% vs 6% in shape fidelity. It decorates given letter shapes; it does not invent new glyph shapes — [arXiv 2406.08392](https://arxiv.org/pdf/2406.08392); [ECCV poster](https://eccv2024.ecva.net/virtual/2024/poster/1762). No public code found.
- **VecFusion** (arXiv 2312.10540, CVPR 2024): cascade where a raster diffusion model produces a low-res glyph conditioned on glyph ID + font style, then a vector diffusion stage — [arXiv 2312.10540](https://arxiv.org/pdf/2312.10540)
- **Text-Conditioned Diffusion Model for High-Fidelity Korean Font Generation** (arXiv 2504.21325, 2025) — [arXiv](https://arxiv.org/pdf/2504.21325)
- **Kuzushiji (cursive historical Japanese) font generation with conditional diffusion** + a web editor (UEC, 2025 conference papers) — relevant as one of the few cursive-script diffusion font works — [UEC paper 1](https://mm.cs.uec.ac.jp/pub/conf24/250108yuan-h_0.pdf); [UEC paper 2](https://mm.cs.uec.ac.jp/pub/conf24/250109yuan-h_0.pdf)

### Inferences
- Reference-count spectrum among the dedicated models: 1 (FontDiffuser, Diff-Font, DiffCJK, One-shot ViT), ~3 (FsFont example), 8 (LF-Font TPAMI), 16 (CF-Font), ~100 (VQ-Font reference pool). A single Arabic word like "مُزن" yields only ~3 letter shapes (م init, ز fina/isol-like, ن fina) plus a damma, i.e. it is in the 1–4 reference regime.
- Resolutions are low for font production: DG-Font is fixed at 80×80; most CJK benchmarks render at 64–128 px (not confirmed per repo here); only HFH-Font explicitly targets higher resolution; MSD-Font uses an SD-2.1 VAE whose checkpoint is named "512". Vectorizing 80–128 px rasters of a decorative display style will lose detail; an upscaling/refinement step would be needed.
- Licensing for a product: MIT code (clovaai FFG, IF-Font, MSD-Font) is usable but ships no weights; FontDiffuser has weights but is research-only. In practice, you would retrain on Arabic data you own, so the font-dataset license (Arabic TTFs) matters more than the code license.
- Compute: no repo gives VRAM figures; CF-Font uses DDP, MSD-Font requires two GPUs for stage 2. Retraining from scratch on a new script = a multi-day, multi-GPU job (inference from comparable repos; not measured).
- Handling of large style deviation: all of these were trained/evaluated on *text* fonts (Founder Type Chinese fonts, Korean fonts). Decorative/display styles such as "inflated balloon" or "fragmented geometric" are far outside the training distribution; component/stroke-based methods (LF/MX/CF/VQ/FsFont) assume a shared stroke/radical vocabulary that a fragmented geometric style breaks. FontStudio-style "effect transfer" handles decorative texture, but not deformation of the skeleton.

## Q2. Arabic: has any model been applied/fine-tuned on Arabic, and what breaks when applying Chinese-trained models to Arabic?

### Takeaway
No few-shot font generation paper or repo found in this research was trained or evaluated on Arabic; the only Arabic generative glyph work surfaced was a StyleGAN2-ada calligraphy generator (Nas4-60k dataset) with unclear attribution. Literature explicitly notes that block-structured (Latin/CJK) methods are ill-suited to Arabic's cursive script with positional letterforms, and text-to-image models show right-to-left and letter-connection failures on Abjad scripts.

### Cited Findings
- A search over Arabic few-shot font generation found no paper modelling Arabic positional forms in a few-shot setting; the one Arabic-specific hit described calligraphic Arabic generation with StyleGAN2-ada trained on custom datasets "Nas4-60k" and "Nas4-60k-aug", and it states prior work centers on Latin/East-Asian scripts "with block letter structures", making them "less suitable for the cursive nature of Arabic script with varying positional letterforms" (note: the page this snippet was attached to is titled as a different paper, so attribution is uncertain) — [ResearchGate listing](https://www.researchgate.net/publication/352832088_Few-Shot_Font_Generation_with_Deep_Metric_Learning)
- FontDiffuser's only cross-lingual demo is Chinese→Korean — [GitHub FontDiffuser](https://github.com/yeungchenwa/FontDiffuser)
- One-shot ViT multilingual generator covers CJK + English only — [arXiv 2412.11342](https://arxiv.org/pdf/2412.11342)
- Ref2Font (FLUX.2-klein LoRA) supports Latin and Cyrillic only; Arabic not mentioned — [GitHub SnJake/Ref2Font](https://github.com/SnJake/Ref2Font)
- digital-rain (FLUX.2-klein + glyph-latent LoRA) lists "Latin only" among its limitations — [GitHub sushiHex/digital-rain](https://github.com/sushiHex/digital-rain)
- A 2025 benchmark of text-to-image models on specialized content found none (Ideogram, DALL·E 3, Stable Diffusion) rendered text correctly outside English, and lists for Abjad scripts (incl. Arabic) "Right-to-left rendering issues" and "Connection problems" — [MDPI Applied Sciences 15(5):2274](https://www.mdpi.com/2076-3417/15/5/2274)
- DrawText (ACL 2023) found T5-based text-to-image encoders cannot accurately render non-Latin scripts, while a character-aware ByT5 encoder did better — [ACL 2023](https://aclanthology.org/2023.acl-long.900.pdf)
- Calligrapher shows results in Chinese, Korean and Japanese; its multilingual demo warns "multilingual output quality may be lower" — [GitHub Calligrapher](https://github.com/Calligrapher2025/Calligrapher)
- FontAdapter was trained only on English, but claims it "effectively captures font features from other language glyphs" (glyph-agnostic training), i.e. style can be taken from one script and applied to another — [arXiv 2506.05843](https://arxiv.org/pdf/2506.05843)
- DuwatBench (arXiv 2601.19898, 2026) evaluates multimodal models on Arabic calligraphy (recognition/understanding, not generation) — [arXiv](https://arxiv.org/pdf/2601.19898)

### Inferences
- Failure modes to expect when a Chinese-trained model is applied to Arabic (inferred from architecture/data, not from a published Arabic experiment):
  1. **Content encoder is out of domain**: the content image (source-font glyph) is an Arabic shape never seen in training; MX/LF/CF/FsFont rely on Chinese component/radical decomposition labels which have no Arabic equivalent.
  2. **Fixed square canvas and centering**: CJK models assume one glyph per square em; Arabic glyphs have wildly varying advance widths (e.g. ـــ kashida, wide fina forms like ـس / ـن), descenders below baseline (ر، و، ن، ي، ع), and tall ascenders (ا، ل، ك). Square-canvas normalization destroys baseline and joining position.
  3. **Joining strokes**: init/medi/fina forms must exit/enter at a consistent baseline height and stroke thickness so that the OpenType font connects; per-glyph generators have no constraint for that, so connections will misalign.
  4. **Dots and marks (i'jam/harakat)**: small detached components are exactly what low-res (80–128 px) generators blur or drop; dot shape is a strong style carrier in display lettering (round dots in balloon style vs. square/diamond in geometric style).
  5. **Style extraction from a joined word**: reference images in these models are isolated glyphs; a logo word such as "مُزن" has to be manually segmented into per-letter crops, and ligature/overlap regions don't segment cleanly.
- The realistic path is to retrain/fine-tune an existing architecture (e.g. FontDiffuser or MSD-Font code) on a corpus of Arabic fonts rendered per positional form (isol/init/medi/fina as separate "characters"), with baseline-aware canvases — this is an engineering inference, not something any source reports having done.

### Gaps
- No published Arabic few-shot font-generation result (quantitative or qualitative) was found; it remains unknown how FontDiffuser/MX-Font etc. perform when retrained on Arabic.
- The Nas4-60k StyleGAN2 Arabic calligraphy paper could not be precisely identified (title/venue/repo).

## Q3. General-purpose diffusion approaches (SDXL/FLUX + IP-Adapter, InstantStyle, StyleAligned, ControlNet, LoRA/DreamBooth, text-rendering models): can they produce consistent per-glyph font output? Evidence of font-making pipelines

### Takeaway
By 2026 the most convincing font-making evidence from general diffusion models comes from FLUX.2-klein LoRA projects that generate the whole charset as one atlas image (Ref2Font, digital-rain), which keeps style consistent across glyphs and ends with a grid-to-TTF script; they are Latin/Cyrillic-only, so Arabic would require training a new LoRA on Arabic atlases. Text-rendering/editing models (Calligrapher, FontAdapter, AnyText-family) render styled words in images but are not designed to emit a consistent per-glyph set.

### Cited Findings
- **Ref2Font (V3)**: contextual LoRA for **FLUX.2-klein-9B**; input = one strictly black-and-white reference image ("Aa" Latin / "Аа" Cyrillic), output = 1280×1280 **font atlas** (A–Z, a–z, 0–9, punctuation); ComfyUI workflow; ships `flux_grid_to_ttf.py`, `flux_pipeline.py`, `glyph_metrics.py`: normalized baseline alignment, edge cleanup, contour tracing, shared line metrics; **MIT**, 98 stars; limitations: "works well, but not perfectly", artifacts, unusual letterforms need manual edits, no kerning or hinting, exact prompts required for character order — [GitHub SnJake/Ref2Font](https://github.com/SnJake/Ref2Font); [Civitai page ("much more stable in V3")](https://civitai.com/models/2361340/ref2font-flux2-klein-9b-fonts-lora)
- **digital-rain** (research repo, notes Jul–Sep 2026): FLUX.2-klein-9B (non-commercial base) / klein-base-4B (Apache-2.0) + rank-32 LoRA + a glyph-latent channel (VAE-encoded template atlas concatenated on channels); trained on **one RTX 3090, ~4.4 h, 5,000 steps**, 925-font corpus, 50-font holdout; draws the other 92 glyphs from **two reference glyphs**; holdout char_acc 0.6917 / DINOv2 0.8788 (9B), *below* a nearest-neighbour retrieval baseline (0.7768 / 0.9389); seed-only training variance char_acc 0.49–0.66; reference-to-atlas match 11/16; failures: "stencil sans with deliberate breaks" came out solid, fine interior detail degrades on narrow glyphs, no spacing/kerning, Latin only; AGPL-3.0 code, **no weights published** (licensing); 2 stars — [GitHub sushiHex/digital-rain](https://github.com/sushiHex/digital-rain)
- **Calligrapher** (arXiv 2506.24123, 2025): built on **FLUX.1-Fill-dev**, takes a masked source image + a reference style image (text or non-text reference), uses SigLIP image encoder; weights `calligrapher.bin` on Hugging Face; 299 stars; no license stated on repo; trained at 512 px (recommends 512/768, high res causes spelling errors); tends to fill the mask; ~4 s/image at 10 steps on an A6000; Chinese/Korean/Japanese shown, multilingual quality "may be lower" — [GitHub Calligrapher2025/Calligrapher](https://github.com/Calligrapher2025/Calligrapher); [arXiv 2506.24123](https://arxiv.org/pdf/2506.24123)
- **FontAdapter** (KAIST et al., arXiv 2506.05843, Jun 2025): generates visual text in unseen fonts from a reference glyph image without inference-time fine-tuning; two-stage curriculum (isolated glyphs → natural backgrounds); ~11 s on one RTX 3090; English-only training but cross-script style transfer; supports font blending by interpolating style tokens — [arXiv 2506.05843](https://arxiv.org/pdf/2506.05843)
- **FontStudio** consistency trick: generate one reference letter's effect, then training-free transfer of that texture to all other letters' masks — [arXiv 2406.08392](https://arxiv.org/pdf/2406.08392)
- **FLUX-Font**: separate LoRAs for glyph structure and style, combinable independently (Chinese) — [Springer 2025](https://dl.acm.org/doi/10.1007/978-981-95-4395-3_23)
- **FontFusion** (2026): typographic conditioning on FLUX.1 [dev], reported font-consistency 0.91% → 76.52% — [arXiv 2606.06066](https://arxiv.org/pdf/2606.06066)
- **FontCrafter** (2026): artistic font creation from element images via visual in-context generation — [arXiv 2603.22054](https://arxiv.org/pdf/2603.22054)
- **STRICT** (EMNLP 2025) text-rendering stress test: GPT-4o and Gemini-2.0 significantly outperform others on character/word accuracy — [ACL Anthology](https://aclanthology.org/2025.emnlp-main.1070.pdf)
- TextDiffuser (NeurIPS 2023) introduced MARIO-Eval for text rendering — [NeurIPS paper](https://proceedings.neurips.cc/paper_files/paper/2023/file/1df4afb0b4ebf492a41218ce16b6d8df-Paper-Conference.pdf); HDGlyph (2025) targets long-tail Chinese/English rendering — [arXiv 2505.06543](https://arxiv.org/pdf/2505.06543)

### Inferences
- **Why atlas generation works**: digital-rain's author attributes cross-glyph consistency to generating glyphs together in one image (shared attention), versus per-glyph independent sampling where IP-Adapter/InstantStyle/StyleAligned only give "similar vibe" not identical stroke weight, contrast, and terminal treatment. For Arabic, an atlas per positional-form set (e.g. a grid of all fina forms) is a plausible adaptation.
- **ControlNet on a skeleton/outline**: conditioning on a rendered neutral Arabic glyph (from a base font) with Canny/scribble/segmentation control + IP-Adapter/LoRA for style is the standard way to preserve letter identity; FontStudio's segmentation-mask condition is a published variant of that idea. Constraint risk: a skeleton from a regular font fights with "inflated" or "fragmented" styles that change silhouette substantially.
- **LoRA/DreamBooth on a few crops from one word**: with ~3 letter crops the LoRA will overfit to those letters; a two-LoRA (glyph vs style) separation like FLUX-Font, or style-only LoRA + structural ControlNet, is the more defensible design.
- **Text-rendering models** (AnyText, TextDiffuser, GlyphControl, Glyph-ByT5, TextCtrl, Calligrapher) target words in scenes; they don't output isolated, baseline-aligned, per-glyph images at controlled metrics, and Arabic support is weak per the MDPI and DrawText findings. They can serve at best as a style-reference "word renderer", not as the font engine.
- **Licensing**: FLUX.1-dev/Fill-dev and FLUX.2-klein-9B are non-commercial bases (digital-rain explicitly cites this for klein-9B); FLUX.2-klein-base-4B is Apache-2.0 (per digital-rain), making it the more product-friendly base for a custom Arabic atlas LoRA.

### Gaps
- Not re-verified in this session (paper pages blocked): IP-Adapter (arXiv 2308.06721, tencent-ailab/IP-Adapter), InstantStyle (arXiv 2404.02733), StyleAligned (arXiv 2312.02133, google/style-aligned), AnyText / AnyText2 (tyxsspa), TextDiffuser-2, GlyphControl, Glyph-ByT5 / Glyph-ByT5-v2 language lists, TextCtrl (NeurIPS 2024). Their licenses, stars and Arabic support must be checked separately; no published evidence was found of any of them being used to build a complete font.
- No source reports a diffusion pipeline producing a complete *Arabic* font (all positional forms).

## Q4. Is "one word → full font" realistic? Reported quality with 1–4 reference glyphs

### Takeaway
One-shot and two-shot generation is an established research setting (Diff-Font, FontDiffuser, DiffCJK, One-shot ViT, digital-rain's two-glyph references), but reported quality is measured on *text* fonts within the training script, and even then quality metrics trail simple retrieval baselines in at least one 2026 measurement; for a decorative Arabic logo style with ~3 distinct letters, a fully automatic result is unrealistic — a human-in-the-loop pipeline (generate → select → edit) is the realistic expectation.

### Cited Findings
- FontDiffuser is designed as **one-shot** (one style reference per generation) — [GitHub FontDiffuser](https://github.com/yeungchenwa/FontDiffuser); [arXiv 2312.12142](https://arxiv.org/pdf/2312.12142)
- DiffCJK generates a wide range of target styles from a **single reference glyph** — [arXiv 2404.05212](https://arxiv.org/pdf/2404.05212)
- Ref2Font generates a full Latin/Cyrillic atlas from one "Aa" image but artifacts occur and unusual letterforms need manual editing — [GitHub Ref2Font](https://github.com/SnJake/Ref2Font)
- digital-rain (2 reference glyphs → 92 glyphs): char_acc 0.69 and DINOv2 0.88 on holdout, both below a retrieval baseline (0.78 / 0.94); author reads these metrics as measuring generic "font-likeness"; high seed variance; deliberate-break (stencil) styles not reproduced; evaluation used oracle references, not user uploads — [GitHub sushiHex/digital-rain](https://github.com/sushiHex/digital-rain)
- "Few-Part-Shot Font Generation" (ICDAR 2025 WML) addresses generating an entire font from a few *partial* glyphs — directly analogous to a logo word where letters are joined/overlapping — [arXiv 2509.10006](https://arxiv.org/abs/2509.10006)
- Classic component-based methods use more references: 8 (LF-Font TPAMI) to 16 (CF-Font) to a ~100-char pool (VQ-Font) — [TPAMI LF-Font](https://dl.acm.org/doi/10.1109/TPAMI.2022.3196675); [CF-Font repo](https://github.com/wangchi95/CF-Font); [VQ-Font repo](https://github.com/Yaomingshuai/VQ-Font)

### Inferences
- For "مُزن", available evidence per form: م (init), ز (non-joining, isol/fina-like), ن (fina), ُ (damma). Missing: dots (ن has one dot — the only dot evidence), all medial forms, letters with bowls/loops (ه، ص، ع), tall verticals (ا، ل، ك), descender families (ي، ج). The model must extrapolate stroke contrast, terminal shape, and joining height from 3 shapes — far less coverage than the 8–16 glyphs component-based papers use.
- Style-type matters: "balloon/inflated" is largely a *global* transform (uniform swell, rounded terminals, possibly outline/highlight) that a style encoder or FontStudio-style effect transfer can plausibly propagate; "angular geometric/fragmented" involves *structural* decisions (where to cut, which curves become straight segments) that are letter-specific and much harder to infer from 3 letters (cf. digital-rain's stencil-break failure).
- A realistic product design: (a) segment the word into letter crops, (b) treat each crop as a reference, (c) generate each positional-form group as an atlas with a structural condition from a neutral Arabic base font, (d) let the user pick/regenerate per glyph, (e) vectorize and auto-fit joining points to a common baseline/stroke height before building GSUB init/medi/fina. Expect substantial manual cleanup for logo-grade quality.

### Gaps
- No paper reports quantitative quality for 1–4 references on a script with contextual joining forms, nor on decorative display styles.
- Standard metrics (FID, LPIPS, SSIM, L1) reported per paper for 1-shot vs few-shot were not extracted because arXiv PDFs could not be opened in this session.
